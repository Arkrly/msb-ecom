# Plan 05-01: Automated Orchestration, Verification & Teach-Back

## Overview
Author the deployment automation scripts (`k8s/deploy.sh`, `k8s/teardown.sh`), end-to-end verification script (`k8s/verify.sh`), and comprehensive architecture documentation (`k8s/README.md`). This phase ties together all prior work into a single-command deploy experience and produces the interview-ready teach-back guide.

## Tasks

<task id="05-01-01">
<title>Author deployment and teardown scripts</title>
<read_first>
- k8s/00-namespace.yaml
- k8s/01-configmaps-secrets.yaml
- k8s/02-databases.yaml
- k8s/03-infrastructure.yaml
- k8s/04-backend-services.yaml
- k8s/05-gateway-frontend.yaml
</read_first>
<action>
1. Create `k8s/deploy.sh` (executable, `chmod +x`) that:
   - Sets `set -euo pipefail` and defines `NAMESPACE="msb-ecom"` and `SCRIPT_DIR` variables
   - Applies manifests in numeric order: `00-namespace.yaml` → `01-configmaps-secrets.yaml` → `02-databases.yaml` → `03-infrastructure.yaml` → `04-backend-services.yaml` → `05-gateway-frontend.yaml`
   - After each tier, runs `kubectl wait --for=condition=Available deployment/<name> -n $NAMESPACE --timeout=<N>s` for every Deployment in that tier
   - Timeout values: databases 120s, infrastructure 120s (keycloak 180s), backend services 180s each, gateway 180s, frontend 120s
   - After all applies, runs `kubectl get pods,svc -n $NAMESPACE` to display final state
   - Prints clear status messages with tier names as it progresses
2. Create `k8s/teardown.sh` (executable, `chmod +x`) that:
   - Sets `set -euo pipefail` and defines `NAMESPACE` and `SCRIPT_DIR`
   - Deletes manifests in reverse order: `05-gateway-frontend.yaml` → `04-backend-services.yaml` → `03-infrastructure.yaml` → `02-databases.yaml` → `01-configmaps-secrets.yaml` → `00-namespace.yaml`
   - Uses `--ignore-not-found` flag on every `kubectl delete` command
   - Prints clear status messages
</action>
<acceptance_criteria>
- `k8s/deploy.sh` exists and is executable (`test -x k8s/deploy.sh`)
- `k8s/teardown.sh` exists and is executable (`test -x k8s/teardown.sh`)
- Both scripts use `set -euo pipefail`
- deploy.sh applies all 6 manifest files in order 00→05
- deploy.sh includes `kubectl wait` for every Deployment (mongo, mysql, postgres-auth, postgres-keycloak, zookeeper, broker, keycloak, mailpit, auth-service, product-service, order-service, inventory-service, payment-service, notification-service, api-gateway, frontend)
- teardown.sh deletes all 6 manifest files in reverse order 05→00
- teardown.sh uses `--ignore-not-found` on all delete commands
- Neither script hardcodes namespace or image names — both use variables
</acceptance_criteria>
<verify>
bash -n k8s/deploy.sh && bash -n k8s/teardown.sh && grep -q "set -euo pipefail" k8s/deploy.sh && grep -q "NAMESPACE" k8s/deploy.sh && grep -q "\-\-ignore-not-found" k8s/teardown.sh
</verify>
</task>

<task id="05-01-02">
<title>Author end-to-end verification script</title>
<read_first>
- k8s/deploy.sh
- k8s/05-gateway-frontend.yaml
</read_first>
<action>
1. Create `k8s/verify.sh` (executable, `chmod +x`) that:
   - Sets `set -euo pipefail`
   - Defines `NAMESPACE="msb-ecom"` and color output helpers (green for pass, red for fail)
   - **Step 1 — Pod Readiness:** Runs `kubectl get pods -n $NAMESPACE --no-headers` and checks that every pod shows `Running` with `1/1` ready. Reports pass/fail count.
   - **Step 2 — Gateway Health:** Runs `curl -sf http://localhost:9000/actuator/health` and checks for HTTP 200. Reports pass/fail.
   - **Step 3 — Frontend Health:** Runs `curl -sf -o /dev/null -w "%{http_code}" http://localhost:4200/` and checks for HTTP 200. Reports pass/fail.
   - **Step 4 — Summary:** Prints total passed/failed with colored final status (green "ALL CHECKS PASSED" or red "SOME CHECKS FAILED") and exits with appropriate code (0 or 1)
   - All curl commands use `--connect-timeout 5 --max-time 10` for timeout safety
</action>
<acceptance_criteria>
- `k8s/verify.sh` exists and is executable (`test -x k8s/verify.sh`)
- Script checks all pods in msb-ecom namespace for Running/Ready status
- Script tests `http://localhost:9000/actuator/health` returns HTTP 200
- Script tests `http://localhost:4200/` returns HTTP 200
- Script exits 0 on all-pass, exits 1 on any failure
- curl commands include `--connect-timeout` and `--max-time` flags
</acceptance_criteria>
<verify>
bash -n k8s/verify.sh && grep -q "localhost:9000" k8s/verify.sh && grep -q "localhost:4200" k8s/verify.sh && grep -q "kubectl get pods" k8s/verify.sh && grep -q "exit 1" k8s/verify.sh
</verify>
</task>

<action>
1. Create `k8s/README.md` with the following sections:

   **## Quick Start (Zero-to-Running)**
   - Prerequisites: Docker, kind, kubectl
   - Step 1: Create cluster — `kind create cluster --config k8s/kind-cluster-config.yaml --name msb-ecom-local`
   - Step 2: Load images — `kind load docker-image msb-ecom/<service>:local --name msb-ecom-local` for each service
   - Step 3: Deploy — `./k8s/deploy.sh`
   - Step 4: Verify — `./k8s/verify.sh`
   - Step 5: Access — `http://localhost:9000` (Gateway), `http://localhost:4200` (Frontend)

   **## Architecture Overview**
   - Dependency chain diagram (text-based): Namespace → Config → Databases → Infrastructure → Backend → Gateway/Frontend
   - List all 16 pods and their roles
   - Describe the tier model (config, database, infrastructure, backend, gateway, frontend)

   **## Manifest Deep-Dive**
   - For each manifest file, explain:
     - What resources it creates
     - Key attributes: labels/selectors, resource requests/limits, liveness/readiness probes, environment variable sources (ConfigMap vs Secret)
   - Explain why `imagePullPolicy: IfNotPresent` is used (local kind images)
   - Explain why NodePort is used instead of Ingress (simplicity for local dev)

   **## Docker Compose vs Kubernetes**
   - Side-by-side comparison table covering:
     - Orchestration model (declarative YAML vs Compose file)
     - Service discovery (DNS names vs Compose service names)
     - Health checks (Kubernetes probes vs Docker healthcheck)
     - Scaling (kubectl scale vs docker-compose up --scale)
     - Networking (ClusterIP/NodePort vs bridge network)
     - Configuration management (ConfigMaps/Secrets vs env files)
     - Storage (PVCs vs Docker volumes)
   - When to use which (interview talking point)

   **## Interview Q&A**
   - Q: Why Kubernetes over Docker Compose for production?
   - Q: What are liveness and readiness probes, and why do they matter?
   - Q: What are resource requests and limits? What happens without them?
   - Q: How does service discovery work in Kubernetes?
   - Q: Explain the difference between ClusterIP, NodePort, and LoadBalancer services.
   - Q: What is a PersistentVolumeClaim and why do databases need one?
   - Q: How would you scale this deployment for production?
   - Each answer should be 2-4 sentences, concise but technically accurate.

   **## Teardown**
   - `./k8s/teardown.sh` to remove all resources
   - `kind delete cluster --name msb-ecom-local` to remove the cluster
</action>
